# 🧠 Тест по компьютерным сетям (Таненбаум, 6-е изд.)

Офлайн-тест на 100 вопросов по книге Э. Таненбаума «Компьютерные сети». Создан в рамках тестового задания как пример рефакторинга.

## 📋 Возможности

- **100 вопросов** с 4 вариантами ответов (включая множественный выбор)
- **Три режима:** все вопросы, случайный порядок, только ошибки
- **Сохранение прогресса** в localStorage (можно закрыть и продолжить)
- **Три темы:** тёмная, светлая, synthwave (автоопределение системной + ручное переключение)
- **Подробный разбор результатов** с цитатами из книги и номерами страниц
- **Доступность (a11y):** семантическая вёрстка, ARIA-атрибуты, навигация с клавиатуры, фокус-менеджмент
- **Адаптивный дизайн** для мобильных устройств
- **Полностью офлайн** – просто откройте index.html

## 🚀 Быстрый старт

1. Скопируйте папку проекта в любое удобное место.
2. Откройте файл `index.html` в любом современном браузере.
3. Пройдите тест! Ваш прогресс сохранится автоматически.

> **Примечание:** для корректного отображения шрифтов при первом запуске нужен интернет (Google Fonts). После загрузки шрифты кэшируются браузером, и тест работает полностью офлайн.

## 🔄 Что было улучшено по сравнению с исходным сайтом (анализ «вайб‑кода»)

Ниже — детальный разбор проблем исходного сайта (тест по ViPNet) и конкретные изменения, внедрённые в моей версии. Каждый пункт объясняет, **почему** исходное решение было плохим и **как** его исправил.

### 1. Архитектура и организация кода

**Проблема:**  
Вся логика находилась в одном HTML‑файле. HTML, CSS и JavaScript были свалены вместе. Глобальные переменные (`mode`, `quizOrder`, `current`, `answers`, `wrongIds`) лежали прямо в `window`, создавая риск конфликтов имён и делая код нетестируемым.

**Решение:**  
- Проект разделён на модули: `index.html`, `questions.js`, `quiz.js` и папка `styles/` с 12‑ю CSS‑файлами. Каждый модуль отвечает за свою зону ответственности.
- Вся логика инкапсулирована в класс `QuizApp`. Глобальных переменных больше нет. Состояние хранится в `this.state`, что исключает случайное переопределение.
- Данные вопросов вынесены в отдельный файл `questions.js`, правильные ответы и источники хранятся прямо внутри объектов — никаких дополнительных массивов `ANSWER_KEY` / `SOURCE_KEY`, синхронизируемых по индексу.

### 2. Безопасность и рендеринг

**Проблема:**  
Исходный код массово использовал `innerHTML` для вставки данных, включая пользовательский прогресс из `localStorage`. Несмотря на наличие функции `escapeHtml()`, риск XSS сохранялся: при любом пропуске экранирования можно было внедрить скрипт.

**Решение:**  
- Все данные, поступающие из `localStorage`, проходят строгую проверку и экранирование.
- Динамические элементы (варианты ответов) создаются через `document.createElement`, а текст вставляется через `textContent` или предварительно экранированный `innerHTML` только для доверенных статических данных.
- Метод `escapeHtml()` используется для всех переменных, попадающих в HTML, включая числа.

### 3. Управление состоянием и сохранение прогресса

**Проблема:**  
Прогресс теста не сохранялся. При закрытии или случайной перезагрузке вкладки пользователь терял все ответы. Режим «Только ошибки» работал только в рамках одной сессии.

**Решение:**  
- Внедрён механизм автосохранения в `localStorage`. После каждого действия (выбор варианта, проверка, навигация) состояние сериализуется.
- При загрузке страницы проверяется наличие сохранённого прогресса. Если он есть, пользователю предлагается диалог «Продолжить или начать заново?» с корректной фокус‑ловушкой для доступности.
- Режим «Только ошибки» сохраняется между сессиями — можно вернуться к ошибкам позже.

### 4. Доступность (a11y)

**Проблема:**  
Исходный сайт был практически недоступен для людей с ограниченными возможностями:
- Отсутствовали семантические теги (`<main>`, `<nav>`, `<article>`, `<fieldset>`, `<legend>`).
- Не было ARIA‑атрибутов: скринридеры не понимали, что происходит.
- Клавиатурная навигация не работала: до вариантов ответа нельзя было добраться без мыши.
- Индикатор фокуса был неявным, цветовой контраст не соответствовал WCAG.

**Решение:**  
- Полная переработка вёрстки с использованием семантических тегов и ARIA‑ролей (`role="radio"`, `role="checkbox"`, `aria-checked`, `aria-label`, `aria-live`).
- Управление фокусом: при переходе между вопросами фокус автоматически переводится на новый контент, чтобы скринридер сразу озвучивал текст вопроса.
- Клавиатурная навигация: все интерактивные элементы доступны через `Tab`, выбор вариантов — через `Space`/`Enter`.
- Улучшенный индикатор фокуса (`:focus-visible`) с контрастом 3:1 и толщиной 3px.
- Добавлена поддержка `prefers-reduced-motion` для отключения всех анимаций у пользователей с вестибулярными расстройствами.

### 5. Дизайн‑система и темы

**Проблема:**  
Одна жёстко заданная тёмная тема с  анимациями (молнии). Цвета использовались напрямую, без переменных. При масштабировании или добавлении светлой темы пришлось бы переписывать все стили.

**Решение:**  
- Все цвета, тени, скругления и шрифты вынесены в CSS‑переменные (`--bg`, `--accent`, `--text` и т.д.).
- Реализованы три темы: **тёмная** (по умолчанию), **светлая** (ручная + авто по системным настройкам) и **synthwave**. Переключение сохраняется в `localStorage`.
- Декоративные элементы заменены на спокойный фон с сеткой и градиентными сферами, которые можно отключить через `prefers-reduced-motion`.
- Все размеры используют относительные единицы (`rem`, `vh`, `vw`), что гарантирует корректное отображение на любых экранах.

### 6. Производительность

**Проблема:**  
- CSS‑анимации молний и дождя были реализованы через `width`/`height` и `background`, вызывая пересчёт макета (layout thrashing) при каждом кадре.
- Статическое использование `will-change` на декоративных элементах приводило к перерасходу памяти.

**Решение:**  
- Анимации переведены на `transform` и `opacity`, которые обрабатываются GPU и не вызывают перерисовку страницы.
- Удалены все статические `will-change`. Анимации оптимизированы так, чтобы не нагружать рендеринг без необходимости.
- Прогресс‑бар использует только `transition: width`, а блик на нём (`shimmer`) реализован через псевдоэлемент с `transform`.

### 7. Обработка ошибок и устойчивость

**Проблема:**  
- Отсутствовала проверка доступности `localStorage`. В приватном режиме Safari или при переполненном хранилище приложение падало.
- Некорректные данные в `localStorage` (например, ручное редактирование) приводили к `JSON.parse` ошибкам без обработки.

**Решение:**  
- Все обращения к `localStorage` обёрнуты в `try/catch`.
- Добавлен метод `isStorageAvailable()`, проверяющий работоспособность хранилища перед использованием.
- Если хранилище недоступно, приложение продолжает работать (просто без сохранения прогресса), а пользователь получает предупреждение в консоль.

### 8. UX‑улучшения

**Проблема:**  
- Кнопка «Повторить ошибки» была доступна даже при отсутствии ошибок, вызывая бессмысленный `alert`.
- Дублировалась навигация: выпадающий список и карта вопросов одновременно.
- Не было обратной связи при неверном ответе (кроме текста «Неверно»).

**Решение:**  
- Кнопка «Повторить ошибки» автоматически деактивируется (`disabled`), если ошибок нет.
- Убран дублирующий `<select>`, оставлена только интуитивная карта вопросов.
- Добавлены анимации `shake` (тряска) и `glitch` (глитч) при неверном ответе, которые привлекают внимание и делают интерфейс более отзывчивым.

### 9. Мобильная адаптация

**Проблема:**  
Исходный сайт имел базовые медиа‑запросы, но интерактивные элементы (точки карты, кнопки) были слишком мелкими для пальцев.

**Решение:**  
- Точки карты вопросов увеличены до 48×48px на мобильных устройствах (соответствует рекомендациям Apple HIG и Google Material Design).
- Кнопки действий растягиваются на всю ширину экрана на маленьких разрешениях.
- Отступы и размеры пересмотрены для комфортного использования одной рукой.

### 10. Документирование и поддерживаемость

**Проблема:**  
Код не содержал ни одного комментария. Разработчику, пришедшему после, потребовались бы часы на понимание логики.

**Решение:**  
- Все публичные методы класса `QuizApp` задокументированы в формате JSDoc.
- Каждый CSS‑файл начинается с краткого комментария, объясняющего его назначение и зависимости.
- Сложные визуальные решения (градиентная обводка, фокус‑ловушка, анимация блика) прокомментированы в коде — объяснено, *почему* сделано именно так, а не просто *что* делает код.
- Создан подробный `README.md` с инструкцией по запуску, структурой проекта и таблицей улучшений.
