# RAG для преподавателя: решения и критерии качества

Дата анализа: 10.09.2026. Это описание оснований выбора и проверяемых компромиссов, а не обещание, что один алгоритм всегда лучший. Реальная точность зависит от PDF, разметки, языка, вопросов и модели.

## 1. Сначала разделяем три задачи

1. **Найти:** определить релевантную книгу, раздел и фрагменты.
2. **Объяснить:** дать ученику связное объяснение с учётом его конкретной ошибки.
3. **Доказать:** привязать утверждение к исходному тексту, странице и при необходимости дословной цитате.

Успех одной задачи не гарантирует остальные. Семантически похожий абзац может не содержать ответа; правильная мысль модели может иметь выдуманную ссылку; существующая цитата может не доказывать утверждение.

Простыми словами: библиотекарь находит книгу, преподаватель объясняет, редактор проверяет ссылку. Не следует поручать проверку ссылки только памяти преподавателя.

Вывод из источников: комбинация лексического и смыслового поиска — обоснованный baseline, но «лучший RAG для всех учебников» не установлен. Числа улучшений из чужих публикаций не переносим на D4Tech без собственного набора вопросов. Интеграции Docling/RAPTOR/GraphRAG здесь не запускались и их результаты на нашей книге не измерялись.

Простыми словами: название технологии не заменяет экзамен. Новый поиск должен сдать тот же набор вопросов лучше старого.

## 3. Что обнаружено в нашем исходнике и книге

Раньше PDF делился внутри страниц на фрагменты по 1200 символов с перекрытием 180; Chroma возвращала четыре результата dense-поиска. Размеры указаны в символах, не токенах. Метаданные были бедными, а текст для модели обозначал главным образом страницу.

В PDF из репозитория 992 физические страницы, 384 записи оглавления и одна страница без извлекаемого текста. Первые пять страниц не имеют PDF page labels. Это проверка структуры файла, а не полный аудит OCR. Значит, оглавление можно использовать, но нельзя автоматически считать номер PDF-страницы напечатанным номером книги.

В этой поставке индексатор сохраняет имя файла, физическую страницу, доступную метку страницы, последний раздел оглавления на данной странице и SHA-256 документа. Это приближение: на странице может начинаться несколько подразделов. Bounding boxes и точные границы разделов ещё не извлекаются.

Простыми словами: «страница 100 в просмотрщике» и «100 внизу листа» могут быть разными страницами. В интерфейсе источников нужно честно различать их.

## 4. Реализованный baseline

- Dense-поиск извлекает не менее 12 кандидатов, но не больше размера коллекции.
- BM25 ищет по тексту и названию раздела. Токенизатор сохраняет кириллицу и обозначения вроде `IEC-104`.
- RRF объединяет ранги: `score(d) = Σ 1 / (60 + rank(d))`, без повторного учёта одного документа в одном списке.
- В prompt попадают первые `RAG_TOP_K` фрагментов (по умолчанию 4, допустимо 1–8), каждый ограничен 900 символами плюс метаданные.
- Блокирующие операции поиска Chroma вынесены в поток через `asyncio.to_thread`.
- Старый индекс сохраняется под резервным именем вместо предварительного удаления. При ошибке продвижения новой коллекции восстанавливается старое имя.

Ограничения: BM25 сейчас пересчитывает статистику всей коллекции для каждого запроса; это корректный, но не масштабируемый baseline для небольшой базы. Нет русского стемминга, обученного reranker, порога «ответ отсутствует» и измеренного улучшения recall. Dense-поиск может вернуть похожие фрагменты без ответа. Перенос поиска в поток не делает Python BM25 бесплатным для CPU.

Простыми словами: сейчас ищем одновременно по смыслу и по словам. Следующий шаг — улучшить выбор и проверку найденного, а не просто отправлять модели больше текста.

## 5. Рекомендуемая целевая архитектура

### Индексация

`документ → структура → разделы → небольшие дочерние фрагменты → индексы`

Для каждого фрагмента хранить `document_id`, редакцию и hash, `section_id`, `parent_id`, физическую страницу, печатную метку (если подтверждена), исходный текст, координаты на странице и версию parser/embedding. Для таблиц сохранять заголовки и связи ячеек; для сканов применять OCR с проверкой качества. Изменение embeddings требует новой версии индекса.

**Parent–child retrieval:** ищем маленький фрагмент, а читаем его вместе с ограниченным родительским подразделом или соседними абзацами. Это наше архитектурное предложение: компактный поиск и достаточно контекста для объяснения. Размер родителя ограничивает токен-бюджет, а не произвольное «вся глава всегда».

### Запрос

1. Проверить пользователя и доступ к документам до retrieval.
2. Если задан точный документ/раздел/страница — сначала использовать метаданные. Не доверять одному пользовательскому `src` как доказательству.
3. Параллельно выполнить dense и lexical retrieval, объединить кандидатов.
4. Reranker оценит релевантность кандидатов вопросу. Его модель выбрать экспериментом на русских технических вопросах.
5. Поднять выбранные фрагменты до родительских абзацев, удалить дубли и уложить в бюджет токенов.
6. Сформировать объяснение и структурированные ссылки на выбранные источники.
7. Проверить цитаты и показать ссылки на страницы. При отсутствии доказательства явно указать ограничение.

Простыми словами: сначала находим нужную полку и страницу, затем читаем соседние абзацы, чтобы не объяснять предложение вне контекста.

### Точные цитаты

Нужен отдельный контракт ответа: `answer`, `citations[{chunk_id, quote, start, end}]`. Сервер сам получает страницу и название из разрешённого документа. `quote` должна совпадать с указанным диапазоном исходного текста; допустимая нормализация явно описывается и не превращает пересказ в цитату. После OCR требуется сверка с изображением страницы для ответственных материалов.

В код добавлена и протестирована только базовая функция `verified_quote` (совпадение после нормализации пробелов). Она **не подключена к потоковому ответу модели** и не гарантирует подтверждённые цитаты в текущем UI. Для гарантии нужно буферизовать структурированные citations до проверки; уже показанный поток нельзя задним числом назвать проверенным. Также необходима отдельная проверка, что цитата поддерживает утверждение, а не просто существует в книге.

Простыми словами: кавычки — обещание точного совпадения. Нельзя ставить их вокруг красивого пересказа.

## 6. Несколько пользователей

Сейчас API проверяет реальную авторизацию, ограничивает активный/ожидающий запрос одним на пользователя **в пределах процесса**. Teacher имеет общий лимит активных генераций и ожидающих запросов в одном процессе. Dockerfile и Compose явно запускают один worker. На GPU не передаётся общий изменяемый диалог пользователей: каждый запрос содержит собственные messages. Тест с 8 параллельными HTTP-запросами проверяет отсутствие смешивания с имитатором модели.

Для нескольких API worker пользовательский лимит не глобален; для нескольких teacher экземпляров не глобален и лимит генераций. Это нельзя исправить дополнительным React-флагом.

Следующий масштабируемый вариант: таблица jobs в PostgreSQL либо Redis Streams с worker-процессами. Запись содержит `job_id`, авторизованный `user_id`, `attempt_id`, тип запроса, hash входа, версию модели/индекса, статус, lease, TTL и последовательность событий. Уникальный ключ идемпотентности включает пользователя и попытку. Планировщик выбирает запросы разных пользователей по очереди; объяснение одного вопроса — отдельная работа, чтобы большой тест не занимал модель на всю пачку. SSE переподключается по номеру события, не запускает генерацию заново. После падения worker lease истекает; повтор допускается, но завершение фиксируется идемпотентно. Права проверяются и при чтении job/result.

Текущая очередь недолговечна: перезапуск теряет ожидание, таймаут требует повтора. Она ограничивает нагрузку, но не гарантирует, что любой наплыв пользователей дождётся ответа. Производственная очередь с состояниями «ожидает/выполняется/готово/отменено» — следующий этап, если это требуется UX.

Простыми словами: один преподаватель может обслуживать много учеников по очереди. Для нескольких преподавателей нужен общий журнал заявок, иначе каждый ведёт собственную очередь и не знает о соседях.

## 7. Как принимать решение о качестве

Подготовить проверенный преподавателем набор минимум 60 вопросов: точные определения, технические идентификаторы, объяснение ошибок, сравнение разделов, таблицы, вопросы без ответа и запросы на цитаты. Для каждого вручную отметить допустимые документы, редакции, страницы и фрагменты. Не считать имеющиеся `src` из банка тестов автоматически эталоном — их нужно сверить с PDF.

Сравнить при одинаковых моделях и бюджете: dense → hybrid → hybrid+reranker → parent expansion → contextual chunks. RAPTOR добавлять отдельным экспериментом на вопросах по главам; GraphRAG — на связях между документами.

Метрики: recall@k правильных фрагментов, MRR первого релевантного результата, точность страницы/редакции, процент валидных цитат, подтверждённость утверждений, корректный отказ при отсутствии источника, p50/p95 времени, память, токены, глубина очереди и доля отказов. Нагрузочный набор: 1/2/5/10/20 пользователей, повторная отправка, отмена, отключение браузера и перезапуск worker.

Предлагаемый обязательный gate: ноль смешиваний пользователей и принятых поддельных цитат в тестовом наборе; остальные численные пороги согласовать после baseline. Это критерий приёмки, а не заявление о достигнутой точности.
